# 知识库强制工作流

## 触发条件

**所有任务**——产品调研、关键词分析、竞品分析、Listing文案、市场概览或简单问答，
只要涉及数据/分析/结论/交付，必须走知识库流程。无条件适用。

## 核心理念

66条规则卡（6系统+54正式+6案例）是无数次返工的血泪教训。
不读知识库就做任务=裸奔=返工。

## 🔴 任务开始——强制读取（不可跳过）

### Step 1: Pull 知识库
```bash
git clone https://github.com/792360923-cmyk/hermes-knowledge-base1.git /tmp/hermes-kb
cd /tmp/hermes-kb && git pull  # 已有则更新
```

### Step 2: 读 INDEX
`read_file /tmp/hermes-kb/INDEX.md`——了解66条规则卡全貌。

### Step 3: 按任务类型读子索引

| 任务类型 | 子索引 |
|----------|--------|
| 产品调研/BSR/竞品 | field + classification + source |
| 关键词/ABA | keyword_index.md |
| Listing文案 | listing_index.md |
| 市场/趋势/需求 | source_index.md |

### Step 4: 读3-5条最相关规则卡
从子索引选出最相关规则卡逐条读取。
- 字段→field_rules（USB细分/电池/遥控/防水/量化）
- 分类→classification_rules（物理形态/配件/图片标题冲突）
- 数据→source_rules（禁编造/来源标注/卖家精灵参数/BSR混用）
- 曾犯过错→failure案例

**⛔ 严禁不开知识库就做任务！**

## 🟢 任务结束——强制终结（不可跳过）

### Step 5: 输出【知识库增量建议】
```
🔴 PENDING-rule: 新规则/约束
🟡 PENDING-fix: 修正已有规则
🟢 PENDING-case: 成功/失败案例
🔵 PENDING-category: 新类目知识
```
无新发现也写：`（无）`

### Step 6: 写入 PENDING
标准知识卡片格式→`/tmp/hermes-kb/PENDING/KB-XXX-XXX.md`

### Step 7: Push GitHub
```bash
cd /tmp/hermes-kb && git add PENDING/ && git commit -m "PENDING: ..." && git push
```
**⛔ 禁止直接写VERIFIED**——须Commander审核。

## 常见陷阱

1. "任务简单不用读"→❌ 简单任务最易省字段而返工
2. "我记住了"→❌ 规则更新，每次读最新INDEX
3. "没新发现跳过PENDING"→❌ 必须输出（无）确认已检查
4. "直接写VERIFIED"→❌ 必须走PENDING审核管线
5. "push失败算了"→❌ 至少本地commit，不能丢PENDING
