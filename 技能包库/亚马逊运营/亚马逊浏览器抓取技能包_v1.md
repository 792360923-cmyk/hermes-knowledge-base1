# Amazon Browser Scraping — Reliable Patterns

## Core Rule: browser_navigate Only

**Playwright headless gets blocked by Amazon.** Do NOT use Playwright, requests, or any headless scraper for Amazon. The only reliable tool is `browser_navigate` (Browserbase stealth browser). Every product page visit must go through `browser_navigate` → `browser_console` extraction.

## Brand Extraction

```javascript
// The ONE selector for brand. No alternatives, no guessing.
document.querySelector('#bylineInfo')?.textContent
  ?.replace('Visit the ','').replace(' Store','').replace('Brand: ','').trim() || 'NO_BYLINE'
```

**PITFALL: NEVER infer brands from titles.** The user will reject any brand not sourced from `#bylineInfo`. Common traps:
- "12 Jumbo Vacuum Storage Bags" — no brand in title → bylineInfo says "HIBAG"
- "15+1 Packs Vacuum Bags" — no brand in title → bylineInfo says "Wfiia"
- "15 Pack Vacuum Storage Bags" — no brand → bylineInfo says "lezecur"

If `#bylineInfo` returns empty/null, mark as `NO_BYLINE`. Do NOT fill from `Sold by`, title parsing, or any other source.

## Interception Handling

Amazon serves "Continue shopping" pages as anti-bot. Pattern:
1. `browser_navigate` → "Click the button below to continue shopping"
2. `browser_click` the button (ref="e4")
3. Redirects to Amazon homepage — do NOT proceed
4. `browser_navigate` to SAME ASIN URL → product page loads

## Amazon Login + Alexa/Rufus AI Shopping Assistant

See `references/alexa-rufus-and-login.md` for:
- Logging into Amazon with a buyer account (Lisa) to get logged-in page access
- Accessing the Alexa/Rufus AI shopping assistant ("Open Alexa panel" button, top-left next to "All" menu) to ask product detail questions
- Pitfalls: login triggers same "Continue shopping" intercept; Rufus panel may render blank in stealth browser; Alexa only restates listing content (cannot invent missing data)

## Rate Limiting

First ~5-10 visits succeed. Then every other may get "Continue shopping". After click + re-navigate, page loads.

**Do NOT delegate Amazon scraping for anything needing per-page judgment** (multi-field extraction, spec/vision parsing, classification). The one safe exception is the mechanical brand-lookup loop — see "Parallelizing the brand-extraction step" under Proven Workflow below.

## BSR Rank Extraction

The `#productDetails_detailBullets_sections1` selector is unreliable — many listings render BSR
in a different details-table variant/layout and the selector returns null. **Search
`document.body.textContent` instead**; it works regardless of which details block Amazon serves:

```javascript
document.body.textContent.match(/Best Sellers Rank[\s\S]{0,200}/)?.[0]
```

## Full Listing Extraction (title/bullets/rating/reviews/BSR in one call)

For listing audits (title, 5 bullets, rating, review count, BSR), pull everything in a single
`browser_console` call after the page loads — avoids repeated round trips per field:

```javascript
JSON.stringify({
  title: document.querySelector('#productTitle')?.textContent?.trim(),
  bullets: Array.from(document.querySelectorAll('#feature-bullets li span.a-list-item'))
    .map(e => e.textContent.trim()),
  rating: document.querySelector('#acrPopover')?.getAttribute('title')
    || document.querySelector('#acrPopover .a-icon-alt')?.textContent,
  reviewCount: document.querySelector('#acrCustomerReviewText')?.textContent,
  bsr: document.body.textContent.match(/Best Sellers Rank[\s\S]{0,200}/)?.[0]
})
```

Not every product page triggers the "Continue shopping" intercept — check the snapshot returned
by `browser_navigate` first; only click+re-navigate if the intercept actually appears.

**PITFALL: BSR regex can return `null` on a page that DOES have a BSR**, even with no intercept
and no scrolling needed — the body-text search intermittently misses on the first paint. Before
concluding "no BSR", re-run `browser_navigate` to the exact same ASIN URL (a clean fresh load, not
a scroll or a re-click) and retry the regex once. It reliably appears on the second load. Only
mark BSR as genuinely absent after this one retry still comes back null.

The matched blob packs multiple ranks together, e.g.:
`"Best Sellers Rank  #623 in Home & Kitchen (See Top 100 in Home & Kitchen)  #8 in Space Saver Bags  ASIN  B0FG285SBT  Customer Reviews"`
— it's usually a broad-category rank AND a sub-category rank plus the ASIN, all concatenated. When
reporting BSR, pull out the specific `#N in <category>` pair(s) relevant to the task instead of
treating the whole blob as one number. BSR is real-time and will differ from any rank numbers a
user references from an earlier session — report what the page shows now rather than trying to
match an expected number.

## Rating Distribution & AI Review Summary (lazy-loaded — must scroll first)

The 5-star/4-star/... histogram and the "Customers say" AI summary are **not in the DOM on first
paint** on many product pages — the elements only populate after the reviews section has entered
the viewport. Call `browser_scroll(direction="down")` **twice** before trying to extract these, or
the console call will return `null`/`undefined` even though the data exists further down the page:

```javascript
JSON.stringify({
  ratingHistogram: document.querySelector('#histogramTable')?.innerText,
  // -> "5 star\n60%\n4 star\n13%\n3 star\n9%\n2 star\n5%\n1 star\n13%"
  aiSummary: document.body.innerText.match(/Customers say[\s\S]{0,600}/)?.[0]
})
```

Older selectors (`.a-histogram-table`, `[data-hook="cr-summarization-widget"]`,
`#cr-summarization-attribute`, `.reviewsMedley`) are unreliable on the current template — prefer
`#histogramTable` and the `Customers say` text-match above. If `aiSummary` comes back null, it
usually just means the ASIN has too few reviews for Amazon to generate one — not an extraction bug.

## BSR: When It's Genuinely Absent From the Page

Beyond the retry-on-fresh-load tip above, some ASINs on the newer listing template don't surface
BSR anywhere in the rendered page at all — not even inside the collapsed "Additional details" /
"Item details" accordion under `#productDetails_feature_div`. If you want to check that accordion,
expand it programmatically (there's no stable `ref` for it in the snapshot):

```javascript
(function(){
  var a = Array.from(document.querySelectorAll('#productDetails_feature_div a'))
    .find(e => e.innerText.trim() === 'Additional details');
  if (a) { a.click(); return 'clicked'; }
  return 'not found';
})()
```

If BSR is still absent after (a) a fresh re-navigate retry and (b) expanding "Additional details",
stop retrying and just report "BSR not shown on page" — this is a real page-content limitation for
that ASIN, not a selector problem to keep debugging.

## Multi-ASIN Iteration Budget

Each ASIN typically costs 5-8 tool calls when doing full-element extraction (navigate, first-screen
console pull, 2x scroll, histogram/AI-summary console pull, possible accordion expand+retry). When
scraping N ASINs in one turn, budget ~7 calls/ASIN up front so you don't run out of iterations
partway through the last ASIN and deliver an incomplete record.

**Real cost driver: every `browser_navigate` to a `/dp/{ASIN}` page returns a full accessibility
snapshot (header nav, category mega-menu, ~500-700 elements) even though you only need 5-6 fields
from it — this alone is several thousand tokens per ASIN, before the console call. For a batch of
50+ ASINs with per-product detail requested (title/brand/price/rating/reviews/date/image), the
realistic ceiling in one turn is usually **10-20 fully-verified ASINs, not 50-60**. Do the math on
requested volume vs. this ceiling *before* starting, not after burning through budget on the first
dozen.

**When requested volume exceeds the realistic budget for one turn:**
1. Scrape a real, fully-verified sample (whatever the budget allows) — every field on every row in
   the sample must come from an actual `browser_navigate`+`browser_console` round trip.
2. For ASINs not yet visited, keep the real ASIN identifiers (they're cheap to harvest in bulk from
   a BSR page or search results — see below) but mark every other field "待核实/未采集" (not
   collected) — never fabricate title/price/rating/etc. for an ASIN you didn't actually visit.
3. Deliver the partial result with an explicit status column/note per row, and offer to continue in
   follow-up batches (e.g. 10-15 ASINs per additional turn). This is a legitimate, honest
   deliverable, not "doing nothing" — the alternative (fabricating the rest) is the actual failure.

## Bulk-Cheap Alternative: Extract Full Cards From a Search/Listing Page

If the goal is "get many products' title/price/rating/review count" rather than deep per-product
detail (bullets, BSR, images, date-first-available), do NOT visit each ASIN individually — extract
directly from a search results page or BSR grid in a **single console call**. This gets 20-50
products' worth of title/price/rating/reviews for the cost of ONE navigate + ONE console call,
versus 2-3 calls per individual ASIN — use it for "find real competitors for X" / "search these
keywords" tasks where the ask is breadth (many products, few fields) rather than depth:

```javascript
(function(){
  var results = [];
  document.querySelectorAll('[data-component-type="s-search-result"]').forEach(c => {
    var asin = c.getAttribute('data-asin');
    var title = c.querySelector('h2 span')?.innerText || c.querySelector('h2')?.innerText;
    var price = c.querySelector('.a-price .a-offscreen')?.innerText;
    var rating = c.querySelector('.a-icon-alt')?.innerText;
    var reviews = c.querySelector('a[href*="#customerReviews"] span, .a-size-base.s-underline-text')?.innerText;
    if(asin && title) results.push({asin,title,price,rating,reviews});
  });
  return JSON.stringify(results);
})()
```

Some result cards lack a `rating`/`reviews` node (too new / not enough reviews) — report those as
missing for that field rather than guessing, not as a batch failure. When the task is "find real
electric/motorized competitors" among search results that mix in manual/hand-crank items or
unrelated product types (e.g. herb/oil infusers showing up under "butter maker machine"), filter
by reading each title for the relevant mechanism keyword (motor/electric/one-touch vs.
hand-crank/manual) rather than trusting the search engine's relevance ranking alone.

## Pitfall: Numeric Spec Mismatches Between Title and Bullets (Same Product)

Sometimes the title and `#feature-bullets` disagree on a hard number for the exact same, legitimate
product — e.g. title says "150mL Essential Oil Diffuser" but a bullet's body text says "With a 100ml
capacity", or the title says "2H and 4H timers" but a bullet says "4 timers". This is different from
the listing-hijack case below (unrelated product content) — it's the same product, just inconsistent
copy on Amazon's own listing. Do not silently pick one number and drop the other, and do not
average/guess a "true" value. Report both values explicitly in the field (e.g. "标题标注150ml，正文
bullets标注100ml，两处矛盾，如实列出") and flag it in a notes/备注 column. This preserves the real
ambiguity in the seller's own content instead of fabricating false precision.

## Pitfall: ASIN Belongs to a Different Product Category Than the Batch Task

When a task hands you a list of ASINs labeled as belonging to one category (e.g. "17个夜灯/投影灯
产品" — night lights/projectors) for structured spec extraction, don't assume every ASIN actually
matches. In one 17-ASIN night-light/projector batch, one ASIN (`B07S3XQFBS`) turned out to be a
completely unrelated product — LED marquee letter lights — not a mismatched title/bylineInfo on
the *same* listing (that's the Listing Hijack pitfall below), but a genuinely wrong-category ASIN
in the input list itself. Do NOT silently skip it, silently force it into the category's field
template, or silently drop it from the output. Instead:
1. Scrape it fully and normally (title/bullets/overview) just like every other ASIN in the batch.
2. Classify its `类型`/type field as `其他(<real product type>)` naming what it actually is.
3. Add an explicit note/备注 flagging that this ASIN does not belong to the requested category —
   e.g. "该ASIN实际为LED发光字母灯，非夜灯/投影灯类目产品，如实标注" — so the user can catch the
   input-list error rather than silently getting a category tag that doesn't apply.
4. Mark category-specific fields (镜片数、投影角度、色温等) as `不适用` rather than fabricating them
   to fit the requested schema.
This preserves a complete, honest record for every ASIN in the batch without either dropping rows
or bending the schema to hide a real category mismatch in the source list.

## Pitfall: Listing Hijack / Title-Content Mismatch

Occasionally an ASIN's rendered `#productTitle` does NOT match its `#bylineInfo` / bullets / images —
e.g. title reads "Hokuvory Electric Butter Churn..." but `#bylineInfo` says "Visit the ECR4Kids Store"
and the bullets describe a metal utility cart. This happens when a listing gets reused/hijacked or a
variation parent points to stale cached title text. **Always cross-check title vs. bylineInfo vs.
bullets content** — if they describe unrelated products, do NOT report the scraped bullets/brand as
that ASIN's real data. Flag it explicitly as a data anomaly ("ASIN listing mismatch — do not use") and
move on; don't silently merge the mismatched fields into your output table.

## Pitfall: User-Supplied ASIN→Brand Mappings Can Be Wrong

When a task hands you a list of ASINs pre-labeled with brand names (e.g. "B09F38SK4K = Zulay"), still
extract `#bylineInfo` yourself and use THAT as ground truth. The provided label may be stale (the ASIN
was later taken over by a different seller) — report the actual scraped brand and flag the mismatch
against the supplied label rather than trusting the input list.

## BSR Page ASIN Extraction

**Current template (2026): `[data-asin]` is the most reliable selector.** The BSR grid
renders each product as a plain DIV carrying a 10-char `data-asin`, and title/rating/rank
all live inside that same element — one `browser_console` call gets the whole grid:

```javascript
(() => {
  const items = [];
  document.querySelectorAll('[data-asin]').forEach(el => {
    const asin = el.getAttribute('data-asin');
    if (!asin || asin.length !== 10) return;   // filter non-ASIN data-asin nodes
    const title  = el.querySelector('a[href*="/dp/"] span')?.textContent.replace(/\s+/g,' ').trim();
    const rating = el.querySelector('i[class*="a-icon-star"]')?.textContent.trim();
    const rank   = el.querySelector('.zg-bdg-text')?.textContent.trim();
    items.push({asin, rank, title, rating});
  });
  return {count: items.length, items};
})()
```

Pitfalls on the current template:
- `.zg-item-immersion` returns **0** (dead selector — don't use it).
- `#gridItemRoot` is the grid *container*, but `el.getAttribute('data-asin')` on it is
  empty — the `data-asin` sits on a child DIV. Query `[data-asin]` directly, not
  `#gridItemRoot`.
- Only ~30 items render per page, and ranks are non-contiguous across pages (#1-30 then
  #51-80; a middle page `pg=3` returns "Page Not Found"). See `amazon-browser-workarounds`
  "BSR Pagination Quirk" — combine page 1 + page 2 for ~60 ASINs.

Older fallback selector (may still work on some templates):
```javascript
Array.from(document.querySelectorAll('.p13n-sc-uncoverable-faceout a[href*="/dp/"]'))
  .map(a => { const m = a.href.match(/\/dp\/([A-Z0-9]{10})/); return m ? m[1] : null; })
  .filter(Boolean).filter((v,i,a) => a.indexOf(v) === i)
```

BSR page 2 URL: `https://www.amazon.com/gp/bestsellers/home-garden/{nodeId}/ref=zg_bs_pg_2?_encoding=UTF8&pg=2`

## Check `#feature-bullets` BEFORE spending vision budget on infographics

**Pitfall discovered in practice (10-ASIN diffuser spec batch):** the assumption below
that bullets "usually" lack detailed specs is often wrong for appliance-style listings.
Capacity ml, timer hours, mist/intensity levels, coverage sq ft, noise dB, light color
count, battery life, and charge time are frequently spelled out in plain text inside
`#feature-bullets li span.a-list-item`. Always pull bullets first with one
`browser_console` call:

```js
Array.from(document.querySelectorAll('#feature-bullets li span.a-list-item'))
  .map(x=>x.innerText.trim())
```

In one batch, bullets alone supplied every requested spec field for 8 of 10 diffuser
ASINs — only genuinely image-only listings needed the vision workflow below. Jumping
straight to `browser_get_images`+vision for every ASIN in a batch wastes ~6-8 tool
calls each when the bullets already have the answer. Read bullets, identify which
specific fields are *still* missing, and only fall back to infographic vision
extraction for those remaining gaps.

## Extracting Detailed Specs from Product Images via Vision (Infographic Parsing)

When the task needs fields that only appear as text baked into product infographic
images (capacity, timer hours, noise dB, coverage sqft, light modes, package contents,
etc. — common for diffusers/humidifiers/appliances) and bullets (checked above) don't
have them, `browser_get_images` + `mcp__image_analysis__analyze_image` (or equivalent
vision tool) is the right combo. That vision tool's parameter is `path`, not
`image_path` — if the first call errors on a missing required argument, re-check
`tool_describe` for the exact schema rather than guessing again.

**Key technique — the image CDN is NOT behind the same bot-detection as product pages.**
`m.media-amazon.com` image URLs work fine with plain `curl` even when direct `/dp/`
navigation is blocked or intercepted. So: use `browser_navigate`+`browser_get_images`
(browser-only) just to discover image IDs, then download and analyze via `curl` +
vision tool without needing the browser again per image.

Steps per ASIN:
1. `browser_navigate` to `/dp/{ASIN}` (handle "Continue shopping" intercept as usual).
2. `browser_get_images` — the gallery thumbnails come back as
   `https://m.media-amazon.com/images/I/{ID}._AC_US100_.jpg`. The first thumbnail ID is
   usually the main product photo; the next 3-6 are the infographic/lifestyle images
   that carry specs.
3. Build full-res URLs by swapping the size suffix: `{ID}._AC_SX1500_.jpg` (or drop the
   suffix entirely for `{ID}.jpg`). Download with `curl -s -o out.jpg <url>` via
   `terminal` — no browser needed for this step, and it's cheap to batch multiple IDs in
   one shell command/loop.
4. Call the vision tool once per downloaded image with a targeted question ("extract
   all text/numbers: capacity ml, timer hours, mist levels, coverage sqft, noise dB,
   light modes, other specs"). One image = one vision call; don't try to pass multiple
   images to one call.
5. Merge findings across the 3-6 images into one structured record per ASIN. Different
   infographics in the same gallery usually cover different fields (one shows capacity,
   another shows the button/light sequence, another shows dimensions) — expect to need
   all of them, not just the first.

**Budget reality — this is far more expensive than simple field scraping.** Full
infographic-based spec extraction costs ~8-10 tool calls per ASIN (navigate + possible
click-retry + get_images + curl download + 3-5 vision calls), not the 2-3 calls/ASIN
for simple brand/price lookups. For N ASINs requiring full spec-image extraction, budget
accordingly — a single turn realistically covers only 3-6 ASINs at this depth, well
below the 10-20 ceiling documented above for text-only field scraping. When the
requested volume exceeds this, deliver a real, fully-processed sample plus an explicit
list of remaining ASINs and offer to continue in follow-up batches — do not thin out
the per-image analysis to fit more ASINs in, and do not fabricate fields for ASINs not
actually processed.

**Pitfall: many infographics simply don't state precise numeric specs.** Diffuser/
humidifier listings frequently market noise level as "Ultra-quiet"/"Whisper quiet" and
coverage as "Large Room" without ever printing a dB or sqft number anywhere in the
gallery. After checking all gallery images, report these fields as "not stated on
listing" rather than treating it as an extraction failure or estimating a number — this
is a real gap in the seller's content, not a missed selector.

**Pitfall: comparison-graphic contamination.** Some gallery images are "Us vs. Them"
comparison infographics (e.g. "NoxLumina: 120ml/1500sqft" next to "Others: 20ml/600sqft").
Vision extraction on these can return numbers that actually belong to the competitor
column, or can hallucinate a plausible-looking full spec table (exact ml/dB/sqft/app-
control) that contradicts the number stated in #productTitle or in other gallery images
for the same ASIN. Always cross-check any vision-extracted number against the title and
against the rest of the gallery before accepting it — if one image's numbers conflict
with the title or the rest of the gallery, distrust that image and mark the field "not
stated on listing" rather than picking one of two conflicting values.

**Pitfall: not every result in a "diffuser"/appliance category is an electronic machine.**
Category listings and search results mix in fundamentally different product types —
scented ballpoint pens, non-electric herbal inhaler sticks, flameless "candle" diffusers
with swappable scent cartridges, water-based air washers. These have no ml/timer/mist-
level/dB/coverage in the electronic-diffuser sense. Read the title and first 1-2 images
before deciding which spec fields even apply; for accessory-type products report the
applicable fields instead (scent/cartridge count, liquid capacity if any, hours-of-use
per cartridge, refill availability) rather than forcing every ASIN into the same
ml/timer/light template and filling the rest with "not stated".

This also covers passive reed diffusers (no electronics — no timer/mist-level/dB field
applies at all) and scent-refill/cartridge packs (an accessory for an existing base unit,
not a standalone device — timer/mist-level/dB are controlled by the base unit, not the
refill). For these, distinguish two different null states in the output rather than
collapsing both into one label:
- "不适用" (not applicable) — the field has no meaning for this product type (e.g. dB for
  a reed diffuser, or timer-levels for a refill pack).
- "未标注" (not stated) — the field does apply to this product type but the listing simply
  didn't publish a number for it.
Still fully scrape title + bullets for these ASINs — don't skip or shortcut them just
because they turned out to be an unexpected type inside a same-category batch.

## Structured Spec Extraction for Night Light / Star Projector / Galaxy Projector / Sunset Lamp Batches

When the task asks for a fixed JSON schema per ASIN for 夜灯/投影灯 products (plug-in sensor
night lights, rechargeable motion night lights, star/galaxy ceiling projectors, sunset-effect
lamps), see `templates/nightlight_projector_spec_fields.json` for the proven field list
(类型/镜片胶片数/色彩数/场景数/分辨率/旋转角度/控制方式/流明/色温/功率/感应/调光/定时/其他功能).
In a 17-ASIN batch spanning all four sub-types, `#productTitle` + `#feature-bullets` alone
supplied every field for all 17 products — zero image/vision calls were needed, so try
title+bullets first here too before reaching for the infographic workflow above.

Classify `类型` by product form first (plug-in wall vs. battery/USB-rechargeable vs. star/galaxy
ceiling projector vs. sunset-effect lamp), then fill sensor/control/color fields accordingly:
- A plain plug-in Dusk-to-Dawn sensor night light legitimately gets `不适用` for
  镜片胶片数/色彩数/场景数/分辨率/旋转角度 — it has none of those attributes, don't force values.
- A star/galaxy projector legitimately gets `不适用` for 感应 — most have no light/motion sensor
  at all, they're on until unplugged or the timer fires, not until dark/motion.
- `分辨率` is almost never stated on consumer star/galaxy projector listings even after checking
  title+bullets+`#productOverview_feature_div`+`#productDetails_techSpec_section_1` — report
  `未标注` without over-searching once those four sources are exhausted.
- Sunset/aurora lamps frequently control color/mode via APP only with no visible physical LM/dB
  spec — if a field like 流明 or 色温 is absent from all four text sources, it is genuinely
  `未标注` for that sub-type, not a missed selector.

## Structured Spec Extraction for Diffuser/Appliance Batches

When a task asks for a fixed JSON schema per ASIN (e.g. "提取准确参数写JSON" for a batch of
diffusers/humidifiers), define the field set once and apply it uniformly — see
`templates/diffuser_spec_fields.json` for the proven field list (类型/遥控APP/容量ml/夜灯/
定时档位/浓度档位/覆盖sqft/静音dB/精油数量/其他功能) and the three null states to use
consistently: an actual value, `"未标注"` (field applies but listing didn't state a number), or
`"不适用"` (field has no meaning for this product type, e.g. dB for a passive reed diffuser).
In one 12-ASIN batch, `#feature-bullets` text alone supplied every field for 11/12 products —
only reach for image/vision extraction (see infographic workflow above) for the rare ASIN where
bullets are silent on a specifically-requested field.

**Type classification for diffuser batches** — classify each ASIN's power/mechanism into one of:
无水 (waterless nebulizing, no water/heat), 加湿 (water-based ultrasonic humidifier), 插电 (AC/USB
mains-powered, no battery), 便携 (battery-powered/portable), 配件 (accessory/refill kit, not a
standalone device). A product can be two of these at once (e.g. "无水+插电" for a plug-in-wall
waterless unit, or "无水+便携" for a battery waterless car diffuser) — report the combination
rather than forcing a single tag.

**Pitfall: word-boundary regex for mechanism keywords.** Classifying by `motor`/`battery`/`hand` with a bare substring match false-positives on unrelated words — e.g. `motor` inside `motorcycles` (the product's *vehicle service type*), `hand` inside `handles`, `battery` inside a vehicle name. Always match with word boundaries (`\bmotor\b`, `\bbattery\b`, `\bhand\b`) and, for the electric-vs-manual call specifically, prefer the electric keywords (battery/cordless/rechargeable/electric/powered/motor/12v/usb-charge/auto-stop) over the mere presence of `hand`/`siphon` — a title reading "Cordless Fuel Transfer Pump, Hand Siphon Pump" is electric, not manual, because the battery/motor signal dominates.

**Pitfall: classify by product FORM, not by keyword, and get the priority order right.** The user rejects keyword-only classification of physical product type. Judge in this order per product: (1) 配件/accessory — no complete working body (hose-only, connector, nozzle, valve, replacement primer-bulb, reed diffuser, refill/cartridge pack, non-electronic inhaler pen); (2) 电动 — complete body with battery/motor/mains/charging/auto-stop; (3) 手动 — complete body driven by hand squeeze/siphon/gravity/plunger/lever; (4) 待核实 — can't tell from title+images. A "hand pump" or "siphon hose" title is NOT automatically manual or accessory — a squeeze bulb / pump body makes it manual, and any battery/electric keyword overrides to electric. Don't invent an intermediate category like "手自一体" unless the user's own rules define one.

## Spec Field Missing From Both Title and Bullets: Check Overview/TechSpec Before Giving Up

When a hard spec (e.g. capacity ml) is absent from `#productTitle` and `#feature-bullets`, check the
two other structured spec blocks before marking it "未标注":

```javascript
JSON.stringify({
  overview: document.querySelector('#productOverview_feature_div')?.innerText,
  techSpec: document.querySelector('#productDetails_techSpec_section_1')?.innerText
})
```

**Pitfall: don't regex `document.body.innerText` for a bare unit like `ml` to hunt for a missing
spec.** On a real listing this pulls matches from the "related products / customers also bought"
carousel further down the page — those belong to *other* ASINs. A 13-diffuser batch hit this:
`document.body.innerText.match(/\d+\s*ml/gi)` returned a dozen plausible capacities, none of which
were actually the scraped product's. Only trust `#productTitle`, `#feature-bullets`,
`#productOverview_feature_div`, and `#productDetails_techSpec_section_1` for spec values; if none
of those four contain it, the field is genuinely absent — report "未标注", don't guess from a
body-wide regex hit.

## Third Null State: "无" (explicitly stated absent) vs "未标注" (listing silent)

Beyond "未标注" (not stated) and "不适用" (not applicable — covered above), add a third state for
fields the listing explicitly denies: when the copy itself says a feature doesn't exist — e.g. "No
apps, no hassle. Just press the button" for app control, or "Fragrance oil not included" for
included-oil count — record that field as **无** rather than **未标注**. These carry different
meaning downstream: "未标注" invites "check yourself / ask the seller"; "无" means "confirmed absent
per the seller's own wording, don't re-ask." When marking a field 无, keep it traceable to the
seller's phrasing (quote or closely paraphrase it) rather than just writing a bare "无".

## Proven Workflow for 50+ ASINs

1. BSR page 1 → extract ASINs + titles
2. BSR page 2 → extract ASINs + titles
3. Each ASIN: `browser_navigate` to `/dp/{ASIN}` → `browser_console` extract `#bylineInfo`
4. Handle intercepts with click + re-navigate
5. Compile Sheet1: 序号/ASIN/品牌/标题/标题翻译/备注

**No shortcuts.** Each ASIN needs its own browser_navigate call.

### Parallelizing the brand-extraction step with delegate_task

When the ONLY field needed per ASIN is the brand, the mechanical navigate→`#bylineInfo`
loop can fan out to parallel leaf subagents (verified on a 60-ASIN Travel Garment Steamer
batch: 3 subagents × ~20 ASINs each, ~4 min wall-clock, 100% accuracy). Requirements:

1. Precise per-subagent instructions: exact `https://www.amazon.com/dp/{ASIN}` URL, the
   `#bylineInfo` selector + strip rules, the "Continue shopping" → click → re-navigate
   recovery, and an explicit "brand must come from #bylineInfo, never guess, mark 待确认
   if empty" rule.
2. Split the ASIN list into ≤20-per-subagent batches and pass the full list inline
   (subagents have no conversation memory; use the leaf role).
3. **Spot-check after the fan-out returns** — subagent results are self-reports. Re-navigate
   to 2-3 ASINs yourself (especially any with a weird-looking brand) and confirm #bylineInfo
   matches before trusting the batch.

This delegation is ONLY for the mechanical single-field brand lookup. Deep multi-field
extraction (bullets/BSR/specs/images/vision) still must be done by the orchestrator.
